## Review remediation

Supervisor review finding (verified against indexmap semantics): `EpochDelta::draw_freshest` documented "within a bucket, insertion order" but could not deliver it. It repeatedly took `set.iter().next()` (the FIRST/oldest-inserted key) then `swap_remove`, which swaps the LAST element into the vacated first slot. For [a,b,c,d] budget 2 the draw was [a,d] and the retained remainder [c,b] — both out of insertion order. Promotion (`record`) used the same `swap_remove`, so promoting a middle key perturbed the old bucket. Every pre-existing test used buckets of at most 2 keys, which is exactly where the swap is invisible.

Invariant landed (ONE order invariant, documented in the module comment, the `Ledger` doc, and the `record`/`draw_freshest`/`take_keys` docs): draw order = bucket recency (newest block first, older buckets after), then strict INSERTION ORDER within a bucket, for BOTH the drawn segment and the retained remainder.
- Whole-bucket drain when the remaining budget covers the bucket: `std::mem::take` (O(n), natural insertion order).
- Partial drain: `IndexSet::split_off(remaining)` — the drawn head (earliest-inserted) keeps insertion order and the retained tail keeps its original order (O(n), order-preserving on both sides).
- Promotion: `IndexSet::shift_remove` (order-preserving, O(n) in the bucket's length) instead of `swap_remove`, so the old bucket is never reordered.
- `take_keys()` doc now states its output is recency-bucket order (newest block first, insertion order within each bucket), NOT the historically-sorted order — one observational sentence; no consumer depends on sorted order (full suite green).

New red-first tests (failed on the current code, pass after the fix):
- `partial_draw_and_remainder_follow_insertion_order` — [a,b,c,d] budget 2 → asserts `[a,b]`, then a follow-up full draw asserts `[c,d]`. RED: left `[pool_id 1, pool_id 4]`, right `[pool_id 1, pool_id 2]`.
- `promoting_a_middle_key_preserves_old_bucket_order` — promote middle key c out of [a,b,c,d]; full draw afterwards must yield `[a,b,d]`. RED: left `[1, 4, 2]`, right `[1, 2, 4]`.

Existing parity/full-draw/rewind/expiry tests were kept unchanged and remain green (the invariant change does not touch their assertions; their buckets are <=2 keys, where the old behavior already matched). `rust/Cargo.toml`'s indexmap comment was corrected from "O(1) `swap_remove` for the promotion path" to the landed shape (`shift_remove` / `split_off` / `mem::take`).

Re-validation: `cargo test -p degenbot-bot --features otel --lib` = 757 passed / 0 failed / 3 ignored; `cargo test -p degenbot-bot --features otel --lib epoch_delta` = 8 passed; `cargo fmt -p degenbot-bot` clean; `cargo clippy -p degenbot-bot --all-targets --features otel` clean; `cargo check --workspace` clean.

Note on the instruction shape: the review instructions proposed a partial drain of "repeatedly taking the LAST element and reversing", which draws the LATEST-inserted keys and contradicts the required behavioral example ([a,b,c,d] budget 2 → [a,b]). I implemented the head-drain (`split_off`) so the drawn segment is the earliest-inserted keys in insertion order, matching the required test and the "insertion order for the drawn segment AND remainder" invariant.
